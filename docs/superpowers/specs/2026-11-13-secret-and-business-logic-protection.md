# حماية الأسرار ومنطق الأعمال — المواصفة

## الهدف
حماية الأسرار فعلياً ومنع تجاوز صلاحيات الطلاب أو المشرفين بنقل القرارات الحساسة إلى حدود موثوقة (قاعدة البيانات أو Supabase Edge Functions)، مع الإبقاء على GitHub Pages واجهة عامة لا تحتوي أسرار خادم.

## ما كشفه فحص المستودع
- الواجهة تنشئ Supabase client باستخدام `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY`. الملف المحلي `.env.local` مستثنى من Git، واحتوى الجرد على أسماء متغيرات الواجهة فقط؛ لم تُطبع القيم أو تُفحص كأسرار خام. المفتاح من صيغة publishable، وهو عام بالتعريف.
- Workflow الخاص بـ GitHub Pages يضمّن عنوان المشروع ومفتاح publishable في بناء الواجهة. هذا ليس سرّاً ولا يمنح صلاحية بحد ذاته؛ لا يجوز استبداله بمفتاح service-role.
- لا توجد `supabase/functions` ولا ملفات إعداد Supabase CLI بالمستودع. توجد استدعاءات إلى `send-push` وإلى `admin_reset_password`، لكن تنفيذ Edge Function وسياسات الجداول الأساسية ليست ضمن الملفات المتاحة.
- خدمات المشرف تقرأ وتكتب جداول مباشرة من المتصفح، ومنها الاشتراكات والإعدادات والإعلانات وموقع الحافلة. أمان هذه العمليات يعتمد على RLS وسياسات الخادم الفعلية، التي لا يمكن إثباتها من المستودع الحالي.
- عمليات الدردشة ورحلات الكوستر لها وظائف SQL محدودة في migrations، وبعضها يفحص دور admin داخل قاعدة البيانات. يجب ألا يُفترض أن هذه تغطي جداول التطبيق الأساسية.

## المتطلبات
1. لا يوجد مفتاح `service_role` أو مفتاح خاص أو كلمة مرور ضمن الشيفرة أو artifact الواجهة أو متغيرات `VITE_*`.
2. كل قرار صلاحية يجب أن يُفحص في PostgreSQL/RLS أو Edge Function موثوقة؛ إخفاء عناصر الواجهة والتحقق في React ليس حدّاً أمنياً.
3. تبقى المفاتيح العامة publishable/anon عامة، مع تقييد البيانات بـRLS وRPC.
4. يجب تدقيق سياسات RLS، GRANTs، ودوال `SECURITY DEFINER` لعمليات التطبيق الأساسية قبل تغييرها؛ لا تُنشأ سياسات تخمينية على مخطط غير موجود بالمستودع.
5. العمليات التي تحتاج صلاحيات Auth Admin أو أسراراً خارجية (مثل إعادة تعيين كلمة مرور مستخدم آخر أو إرسال push) لا تعمل بمفتاح service-role في المتصفح؛ تنفذ على Edge Function تتحقق من JWT ودور المشرف وتتحقق من المدخلات.
6. لا تُطبّق migrations أو تُنشر Edge Functions على مشروع Supabase حي دون صلاحية ونطاق تنفيذ مؤكدين؛ تُقدّم SQL للمراجعة أولاً.
7. تُضاف اختبارات تثبت فشل وصول طالب إلى عمليات المشرف حتى عند استدعاء RPC/HTTP مباشرة، وعدم تسرب الهوية أو الأسرار.

## خارج النطاق
- تشفير JavaScript/HTML المنشور على GitHub Pages بهدف جعله غير قابل للاستخراج؛ ذلك غير ممكن للواجهة التي تعمل في المتصفح.
- إخفاء مفتاح Supabase publishable أو اعتبار نقله إلى GitHub Variables حماية له.
- تدوير مفاتيح لم يثبت تسربها. إذا كشف المسح التاريخي عن secret حقيقي، يُبلّغ المستخدم باسم نوع المفتاح فقط ويُوقف النشر حتى تدويره من مزوّده.
- تنفيذ migrations أو ضبط أسرار Supabase في الإنتاج من دون موافقة منفصلة.

## معايير القبول
- تقرير جرد لا يطبع قيم أسرار، يحدد جميع العمليات الحساسة وحدود الثقة والملفات/السياسات التي يتطلب التحقق منها.
- اختبار آلي يمنع تضمين أسماء مفاتيح الخادم أو أسرار معروفة في ملفات الواجهة والـbuild artifact مع السماح الواضح بمفتاح publishable.
- كل وظائف الخادم الجديدة تتحقق من هوية المتصل ودوره server-side، وتستخدم أقل صلاحية لازمة، وتفشل مغلقة.
- توجد اختبارات محلية لاختبارات المصادقة والصلاحيات والتحقق من المدخلات وحالات الخطأ.
- `npm test` و`npm run build` و`git diff --check` ناجحة.
- يوثّق بوضوح أي بند يتطلب استخراج مخطط/سياسات Supabase الحية أو تعيين أسرار Edge Function من مالك المشروع، دون طلب مشاركة المفاتيح في المحادثة.
